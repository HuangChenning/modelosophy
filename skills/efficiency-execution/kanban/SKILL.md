# 看板 Kanban

## 这是什么

**看板**：把工作项放在可视化列（如待办/进行中/完成）上，**限制 WIP**，用拉动而非推送来管理流动；目标是看见排队与阻塞、缩短周期时间、提高可预测性。源于丰田拉动信号，后扩展到知识工作。

## 什么时候用

- "团队任务黑洞，不知道卡在哪"
- "看板 / WIP / 在制品限制"
- 运维、产品交付、个人可视化流

**不要**当主模型：

- 固定冲刺节奏与评审 → [`agile-iteration`](../agile-iteration/SKILL.md)
- 项目网络最长路径 → [`critical-path`](../critical-path/SKILL.md)
- 个人收集澄清 → [`gtd`](../gtd/SKILL.md)

## 怎么用（执行步骤）

1. **画出真实价值流列。** 列名反映实际状态（含「等待评审」），不要假想完美流程。
2. **设定 WIP 上限。** 每列进行中上限；超限先完成或协助，不新开。判据：是否经常撞上限。
3. **拉取规则。** 下游有空位才从上游拉；禁止把任务推进下游制造假进度。
4. **管理阻塞。** 阻塞项标出并设升级；度量周期时间与吞吐量。
5. **小步改政策。** 根据数据调列与 WIP，一次改一个政策。
6. **与批量开会分离。** 看板是流系统；需要固定迭代时可与敏捷连用，但不强制。

## 例证

**开发团队**：Code Review 列 WIP=2，暴露评审瓶颈——揭示限制在制品的诊断力。

**个人看板**：Doing≤3，减少同时开坑——揭示个人亦可限 WIP。

## 什么时候不适用（边界）

- **强固定范围与关键路径工期合同**：或需关键路径为主。
- **完全无团队协作的一锤子任务**：轻量清单即可。
- **把看板当状态汇报墙无 WIP**：失去方法核心。

## 常见误用

- **无限 Doing**：无 WIP → 必须设限。
- **列太多装饰**：流程更糊。
- **与 Scrum 仪式强绑**：看板可独立。
- **推送假完成**：跳过政策。

## 相关模型

- **与[敏捷迭代](../agile-iteration/SKILL.md)**：敏捷强调时间盒迭代；看板强调流动与 WIP。可混合（Scrumban）。
- **与[精益思维](../lean-thinking/SKILL.md)**：看板常是精益拉动落地工具。
- **与[TOC](../../cognitive-thinking-tools/theory-of-constraints/SKILL.md)**：瓶颈暴露后可用 TOC 强化。
- **与[GTD](../gtd/SKILL.md)**：个人澄清 vs 团队流。
- **与[PDCA](../pdca/SKILL.md)**：改 WIP 政策用 PDCA。

## 记忆钩子

先**限制同时做的事**，让排队与瓶颈可见，再加速。
