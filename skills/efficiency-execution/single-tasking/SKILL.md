# 单任务处理 Single-Tasking

## 这是什么

**单任务处理**：在任意一段时间内只主动接收、处理一个任务或输入源，拒绝同时并行两个都需要占用注意力的活动，并在切换任务前主动完成收尾，而不是被打断式地切出去。

它是一套**操作纪律**，不是一套理论。理论支撑来自认知心理学对任务切换的测量（详见 [`task-switching-cost`](../task-switching-cost/SKILL.md)：切换有可测量的反应时间和错误率代价，且做到一半被打断比做完再切代价更大）；单任务处理要回答的问题是"知道了这个代价之后，具体该怎么安排自己的工作方式"。管理顾问 Devora Zack 在《Singletasking》（2015）中把这套做法系统化为一个可操作的实践标签，但其中每一条具体建议的有效性，最终都要回到切换成本与注意力残留的研究去检验——这本书本身是实践方法论整理，不是独立的实证研究。

**关键鉴别**：人在感觉上"同时做两件事"时，绝大多数情况下并不是真的同时处理，而是在两者间快速交替（rapid switching）——这也是为什么单任务处理的第一步是先戳破"我在多任务"这个自我感知，而不是直接讲纪律。

## 什么时候用

用户出现以下意图时启用本 Skill：

- "我总是同时开着好几个任务/标签页，切来切去"
- "怎么才能不被手机通知一直打断"
- "想戒掉一心多用的习惯，该怎么做"

**不要**在以下情况套用本模型：

- 用户只是想知道"多任务处理真的有代价吗、有什么研究依据" → [`task-switching-cost`](../task-switching-cost/SKILL.md)，本模型不重复讲机制
- 用户想设计的是一整段无干扰、高认知投入的专注时段（时长、仪式、环境） → [`deep-work`](../../learning-growth/deep-work/SKILL.md)；单任务处理可以是深度工作时段内的一条子规则，但本身不等于深度工作
- 用户手头是一堆同质、低认知负荷的琐事，问题是"该怎么安排这些任务的顺序"而不是"该不该同时做" → [`batching`](../batching/SKILL.md)

## 怎么用（执行步骤）

1. **先确认这是不是真正的同时性。** 判据：回忆最近一次"多任务"的具体场景——两件事是否真的在同一时刻发生，还是在几秒到几分钟内来回切换？如果是后者，问题不是"能不能同时做两件事"（本来就不能），而是"切换频率是不是太高"，直接进入下一步。
2. **开始一项任务前，先屏蔽会引发切换冲动的输入源。** 判据：关掉不必要的通知、把手机移出触手可及范围、只保留当前任务需要的窗口/标签页。能否说清"接下来这段时间，除了当前任务，我不会主动打开什么"。
3. **设定"做到什么程度才允许切换"的收尾判据，而不是被打断就切。** 判据：任务是否已到达一个自然停顿点（一个完整段落写完、一个函数改完并测试通过）？如果还没到，先问自己"现在切走，回来时要花多久才能捡回状态"——这正是注意力残留的代价（Leroy 2009，见 [`task-switching-cost`](../task-switching-cost/SKILL.md) 的例证）。
4. **如果必须在未完成时被迫切换，先把状态外部化再切。** 判据：能否用一句话写下"下一步具体要做什么"（比如"下一步：把这个函数的第 3 个分支测试补上"），而不是只在脑子里记着。这一步直接针对注意力残留——把状态挪到纸面上，减少它继续占用工作记忆的部分。
5. **发现自己一天里被迫切换次数过多，先诊断来源再决定对策。** 判据：切换是被外部打断（他人消息/会议）驱动，还是自己主动分心？前者考虑用批处理窗口集中处理同类打断（见 [`batching`](../batching/SKILL.md)），后者才是单任务处理本身要解决的自我纪律问题——把两者混为一谈会导致"怪自己意志力不够"，其实是外部输入节奏没设计好。

## 例证

**Mark, González & Harris（2005，CHI《No Task Left Behind?》）的办公室现场观察**：研究者跟踪知识工作者的真实工作日，发现被试在细粒度的单个"事件"（event）上平均只停留约 3 分钟就会转向别的事，而在更粗粒度的"工作球"（working sphere，指一个项目/主题的整体工作线）上平均停留约 10–12 分钟才切换；其中 57% 的工作球会被打断，且这类切换相当一部分是自我发起，而非全部由外部打断造成。揭示：单任务处理要对付的敌人，很大一部分不是"别人打断我"，而是自己在无意识地主动切出去——这正是第 1 步"先确认这是不是真正的同时性"存在的原因；同时也提醒不要把"事件"和"工作球"这两个不同粒度的数字混着引用。

**"一次只开一个浏览器标签页"式实践的局限**：一些生产力写作把单任务处理简化为"物理上只留一个窗口"，这类建议的问题是它只处理了环境线索（第 2 步），却没处理"任务做到一半被迫切走怎么办"（第 3、4 步）——只关窗口不解决注意力残留问题，这也是本模型比单纯"关掉干扰"更完整的地方。

**"一心多用效率更低"式通俗举例的局限**：通俗材料常直接引用"多任务让人变笨"的结论式说法，却不说明这个结论具体测的是什么（反应时间？错误率？完成总时长？）。局限在于容易让读者以为"任何形式的并行都有害"，从而忽略了下方常见误用里提到的例外——真正自动化、不占用同一认知资源的搭配（如散步听播客）并不在此列。

## 什么时候不适用（边界）

- **两个活动不共享同一注意力/工作记忆资源**：如散步时听播客、听轻音乐做重复性体力劳动——这类搭配不消耗执行控制资源，强行拆成"先散步再听"反而无谓地降低效率。判据见 [`task-switching-cost`](../task-switching-cost/SKILL.md) 的边界条款。
- **岗位职责本身要求高频响应/切换**（客服、急诊分诊、交易台）：单任务处理的纪律在这类场景下无法落地，应转向响应协议设计（分级、排队、状态标识），而非要求个人"专注一件事"。
- **只是需要快速浏览筛选大量轻量信息**（收件箱扫一遍找紧急项）：这个阶段本身就是"快速切换式扫描"，先按 [`inbox-zero`](../inbox-zero/SKILL.md) 的处理逻辑走一轮分类，再对筛出的需要深度处理的项启用单任务处理。

## 常见误用

- **把"减少切换"等同于"永不允许中断"**：过度追求单任务处理，拒绝一切他人求助或紧急消息 → 单任务处理管理的是自我工作节奏，不是拒绝团队协作；确实紧急的中断仍要响应，只是响应方式可以是"先记下当前状态再切"（第 4 步），而不是干脆不响应。
- **用"我在单任务"给拖延真正该做的事找借口**：借口"专注当前这件"来回避另一件更重要但让人不适的任务 → 这不是任务切换问题，是任务优先级/回避问题，该走 [`eisenhower-matrix`](../eisenhower-matrix/SKILL.md) 或 [`eat-the-frog`](../eat-the-frog/SKILL.md)。
- **把"物理上关掉通知"当成万能解**：只做第 2 步不做第 3、4 步，遇到必须切换的场景仍然状态全丢 → 收尾判据和状态外部化同样重要，缺一不可。
- **对所有并行活动一刀切禁止**：把散步听播客这类不占用同一资源的搭配也当成"多任务"戒掉 → 参考边界条款，区分资源是否共享。

## 相关模型

- **与[任务切换成本](../task-switching-cost/SKILL.md)**：本模型是操作纪律（怎么做），对方是研究机制（为什么有代价）。用户想要行动步骤走本模型，想理解原理或找研究依据走对方；两者常连用——先用对方说服自己/他人"切换确实有代价"，再用本模型落地成具体安排。
- **与[深度工作](../../learning-growth/deep-work/SKILL.md)**：deep-work 设计的是一整段（通常数十分钟到数小时）高认知投入、无干扰的专注协议，包含时长、仪式、环境等完整设计；本模型只管"同一时刻只做一件事、切换前先收尾"这一条纪律，可以是 deep-work 时段内的子规则，也可以单独用在不追求"深度"的日常任务上。
- **与[批处理](../batching/SKILL.md)**：批处理解决的是"同质、低认知负荷的琐事要不要集中处理"，本质上是刻意设计好的、低代价的切换节奏；本模型解决的是"任意两个任务要不要同时/交替处理"。两者常配合：用批处理把打断源集中到固定窗口，窗口之外的时间用单任务处理保护。
- **与[番茄工作法](../pomodoro/SKILL.md)**：番茄工作法是一种带固定计时和强制休息的执行节奏工具；本模型是不依赖计时器也成立的更底层原则——用番茄计时时，"25 分钟内只做一件事"正是单任务处理在具体落地。

## 记忆钩子

一次只接一件事；没到收尾点被迫切走，先把"下一步"写下来再走。
