# 如何应用"麦肯锡式"方法论

用户要求这份报告"类似麦肯锡的方式方法"。这句话容易被理解成"做一套深蓝色封面+目录+章节编号的PPT感报告"——那是视觉模仿，不是方法论。这份文件讲的是几条真正决定一份分析报告是否专业的写作纪律，视觉呈现交给 `assets/report_template.html`（Apple 风格设计），内容纪律要靠你自己在 Step 3 执行时把住。

## 1. 结论先行（金字塔原理）

麦肯锡咨询报告的核心写作原则：**每一层内容都先给结论，再给支撑它的论据**，而不是按"背景→过程→结论"的时间顺序或调查顺序写。具体体现在：

- 报告最前面是 `executive_summary`，用 3-5 条判断把整份报告"提前剧透"完——一个只看执行摘要的人，也应该知道这家公司的关键情况和最值得关注的信号。
- 每个章节（比如"招投标情况"）的第一句话/第一段，也应该是这一章的结论（比如"该公司近3年IT招投标呈现供应商高度集中的特征"），后面才是具体的招投标记录表格作为支撑证据。不要让读者读完整张表格才自己总结出这句话。
- 你写作的顺序和读者阅读的顺序是相反的：你必须先做完检索、看完所有证据，才能压缩出结论；但呈现时结论要放在最前面。这就是为什么 SKILL.md 里反复强调"执行摘要最后写、放最前面"。

## 2. MECE（相互独立，完全穷尽）

拆解一个问题时，子项之间不重叠、合起来覆盖全貌。在这份报告里体现在两处：

- **板块划分本身是 MECE 的**：公司基本面、战略、IT现状、IT投入、招投标、决策链、业务架构、SWOT 这几块尽量不互相包含对方的内容。比如"近5年业务发展"（company_basics）和"战略方向"（strategy）容易写重复——前者是"发生过什么"，后者是"未来打算做什么"，写的时候提醒自己按这个边界分。
- **决策链的角色划分要尽量穷尽已知信息里出现的所有角色**，不要只挑你觉得重要的一两个人写，剩下的漏掉——哪怕某个岗位只知道职能不知道姓名，也要在 `diagram_nodes`/`roles` 里占一个位置，这样读者看到的是完整的决策结构，而不是你筛选过的片段。

## 3. 证据分级，而不是笼统的"据了解"

麦肯锡分析师的报告里几乎不会出现"据了解""业内人士表示"这种无法验证的措辞——每个判断要么明确来源，要么明确标注是推断/待核实。这份报告用三档置信度标签（已证实/推断/待核实）+ 来源编号（`[S1]`）来实现同样的效果，具体规则见 `report-structure.md` 开头和 `SKILL.md` 的核心原则。**这是这份报告"专业感"真正的来源，比配色和排版重要得多**——一份视觉精美但结论没有证据支撑的报告，本质上和一份没有格式的猜测没有区别。

## 4. 一页一个观点，图表服务于结论

麦肯锡的图表几乎不会为了"好看"而画，每张图都对应一个明确的"so what"（比如"供应商集中度在下降"，而不是"这是一张供应商份额图"）。落到这份报告的执行细节：

- 图表选型遵循 `dataviz` 技能的方法（比如供应商份额用排序条形图而不是饼图，参见 `assets/report_template.html` 的实现），但**选对图表类型只是及格线**，真正重要的是每张图旁边要有一句话点出这张图在说明什么，而不是让读者自己去猜。
- `it_bidding.trend_analysis`、`business_architecture.layers[].attention_points` 这些文字字段，都要求"引用具体证据支撑判断"，这也是同一条原则的体现：结论不能悬空，必须能指回某条具体记录或来源。

## 5. 诚实的不确定性，而不是把报告填满

麦肯锡报告里经常出现"需要进一步验证""数据不足以支持结论"这类表述——这不是分析师能力不够，而是专业的一部分。这份报告的 `open_questions` 板块就是把这条原则结构化：与其把不确定的内容也写得斩钉截铁，不如诚实列出"还不知道什么、下次接触要问什么"，这份清单本身对销售的价值往往不低于已经查清楚的部分。

## 落地检查清单

写完 `data.json` 后，用这五条快速自查：

1. `executive_summary.headline` 是不是一句话就说清楚了"这家公司现在什么情况、该关注什么"？
2. 每个章节的第一句话是不是这一节的结论，而不是背景介绍？
3. 有没有哪个判断只写了结论没写来源/置信度？
4. `open_questions` 里的每一条是不是都说清楚了"为什么重要"和"该问谁"？
5. 通篇有没有不小心写出产品推荐、竞品对比或报价——如果有，删掉，那是另一个技能的工作（见 SKILL.md"范围边界"）。
