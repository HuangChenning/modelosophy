# 收件箱清零法 Inbox Zero

## 这是什么

**收件箱清零法**：由 Merlin Mann 在其博客 43 Folders 和 2007 年 Google Tech Talk 演讲中提出，核心不是"让未读数字变成 0"，而是**把大脑从"这封邮件我还没处理、还要惦记"的持续心智负担里解放出来**。方法上，是在固定的处理窗口内，对收件箱里每一条从上到下逐条过一遍、只经手一次，用五个动作分类到底：**删除（Delete）、转交（Delegate）、回复（Respond）、推迟（Defer）、执行（Do）**。

Mann 本人后来在多次公开澄清中反复强调："zero" 指的是**你的大脑在同一封邮件上反复循环的心智周期趋近于零**，而不是收件箱数字必须常年挂零。这个澄清很重要——这套方法被后来的通俗传播窄化成"每天必须把收件箱清成 0 封"的强迫性打卡行为，恰恰违背了它本来要解决的问题（减少焦虑），反而制造了新的焦虑源。

## 什么时候用

用户出现以下意图时启用本 Skill：

- "邮箱/消息堆积如山，不知道从哪下手"
- "收件箱清零 / inbox zero 具体怎么操作"
- "每次收到消息都想马上处理，但越处理越乱"

**不要**在以下情况套用本模型：

- 用户想重建的是**跨所有渠道**（邮件、纸质、脑内想法、会议待办）的完整个人事务系统 → [`gtd`](../gtd/SKILL.md)；本模型只处理收件箱/消息这一个输入渠道
- 用户已经在逐条处理收件箱，纠结的是"这一条具体该不该立刻做掉"这个单点判断 → [`two-minute-rule`](../two-minute-rule/SKILL.md)，两者常连用（见下方"相关模型"）
- 用户的岗位职责就是要求实时响应（客服、值班支持），问题其实是"响应节奏该怎么设计"，不是"收件箱该怎么清" → 需要的是团队级的响应协议，本模型的批处理窗口假设不成立

## 怎么用（执行步骤）

1. **设定固定的处理窗口，不做全天候实时监看。** 判据：能否说清"今天我会在几点、几次集中处理收件箱"，而不是"消息一来就看一眼"。持续监看本身就违背了这套方法要解决的问题——它假设的前提是批处理，不是实时响应。
2. **处理时从上到下逐条过，每条只经手一次就分类完，不许"先扫一眼跳过、之后再回来看"。** 判据：这条邮件是否已经被归入五个动作之一？还停留在"已读但没分类"的状态就不算处理完。
3. **对每条应用五个动作之一：**
   - **删除**：判据——不需要行动也不需要留存记录，直接删。
   - **转交**：判据——这不是该由我做的事，能否一句话说清转交给谁、需要他做什么。
   - **回复**：判据——能否在当前窗口内直接写完回复；如果预计在两分钟左右能写完，直接按 [`two-minute-rule`](../two-minute-rule/SKILL.md) 的判据立即做掉。
   - **推迟**：判据——需要行动但现在做不完，是否已经把它转成一条**带下一步动作**的任务并排进日程/任务清单（而不是让它继续原地躺在收件箱里"留着"）。
   - **执行**：判据——如果本身就是能立刻做完的具体动作（不只是回复），是否已经当场做完再归档。
4. **处理完一轮后，收件箱里不再有"看过但没归类"的邮件，但允许有已处理、留作参考的归档项。** 判据：问自己"这条邮件还需不需要我的大脑继续想它"，而不是"收件箱页面上还显示不显示它"——已推迟到任务清单、已归档的参考资料不算"没清完"。
5. **警惕把"未读数字是不是零"本身当成目标。** 判据：如果发现自己因为收件箱显示"3 封未读"而焦虑、反复打开检查，这正是 Mann 本人后来公开澄清要纠正的误解——真正该检验的是"这些邮件有没有还在占用我的心智周期",不是页面上的数字好不好看。

## 例证

**Merlin Mann 的"5 个动作"分类法（2007 Google Tech Talk）**：Mann 在演讲中明确给出 Delete / Delegate / Respond / Defer / Do 这五个动作作为处理收件箱的完整分类集合，并强调"每条只经手一次"（touch it once）——揭示：这套方法的核心价值不是某个神奇技巧，而是**把"待处理"这个模糊状态拆成五个具体、互斥的终态**，消除"已读但悬而未决"这种最消耗心智的中间态。

**Mann 本人对"零焦虑症"的澄清**：随着"Inbox Zero"一词被广泛传播，大量用户把它简化理解为"必须让收件箱数字保持为 0"，进而发展出频繁刷新检查、为了清零而清零的强迫行为。Mann 本人多次公开纠正这个误解，强调 zero 指的是**花在同一条消息上纠结的心智周期趋近于零**，而不是显示的未读数。揭示了本模型最容易被误解、也最需要在应用时提前说明的一面——这也是为什么第 5 步专门单独列出。

**（原书卡片）"每天固定时间查两次邮件"式举例**：通俗材料常把 Inbox Zero 简化为一条时间管理小贴士（"别整天开着邮箱"），这类表述的局限是只讲了第 1 步（批处理窗口），完全没提到五个动作分类和"经手一次"原则——只做时间管理不做分类处理，收件箱照样会在下次打开时重新堆积成一团模糊的"待办数量"，没有解决真正的心智负担问题。

## 什么时候不适用（边界）

- **高频实时响应岗位**：客服、值班运维、社区管理等职责本身要求接近实时地响应，批处理窗口的前提不成立；这类场景需要的是团队级的分级响应协议（谁负责一线、多久内必须响应），不是个人收件箱清理法。
- **收件箱本身承载了远超"消息"范畴的内容**（项目管理、审批流转都走邮件）：这种情况下邮件已经变相成为任务管理系统，单靠五个动作分类不够，需要先把这些职能拆分到专门的项目管理工具，再回头清理真正的通讯类收件箱。
- **需要跨渠道统一管理所有待办事项**：本模型只处理"收件箱"这一个渠道；如果目标是让脑内所有开放循环（不只是邮件）都有处，需要整套 [`gtd`](../gtd/SKILL.md) 系统，Inbox Zero 可以看作 GTD 收集-澄清流程在邮件这一个渠道上的具体应用。

## 常见误用

- **把清零本身当成目标，为了清零而清零**：反复刷新检查未读数、为了让数字好看而囫囵吞枣式"已读全清" → 回到第 5 步，检验的是心智负担有没有真正解除，不是数字好不好看。
- **实时处理，而非批处理窗口**：消息一来就打断当前工作去处理 → 这恰恰违反第 1 步的前提假设，应转到固定窗口处理；如果打断源本身是外部消息，这是 [`batching`](../batching/SKILL.md) 该解决的问题，不是靠"更勤快地清"能解决的。
- **把"已读"当成"已处理"**：扫了一眼、心里觉得"知道了"但没有归入五个动作之一 → 仍然占用心智周期，不算处理完，回到第 2 步补上分类动作。
- **推迟项没有转成带下一步动作的任务，只是留在原地"以后再看"**：邮件表面上移出了收件箱视野，但因为没有具体下一步，实际上还是心智负担 → 走两分钟法则或直接转成 GTD 意义上的"下一步行动"。

## 相关模型

- **与[GTD](../gtd/SKILL.md)**：GTD 是覆盖所有输入渠道（邮件、纸质、会议、脑内想法）的完整个人事务管理系统，收集、澄清、组织、回顾、执行五个阶段缺一不可；本模型只是把 GTD 的"收集-澄清"逻辑，专门套用到"收件箱"这一个渠道上，动作集合（五个动作 vs GTD 的下一步行动判断）也更精简、更针对邮件场景。用户问"整个工作系统该怎么整理"走 GTD，问"邮箱怎么清"走本模型；两者可以连用——本模型处理出来的"推迟"项，就流入 GTD 的下一步行动清单。
- **与[两分钟法则](../two-minute-rule/SKILL.md)**：两分钟法则是判断"这一条具体该立刻做还是该记下来"的单点启发式；本模型是处理整个收件箱的完整流程框架，其中"回复/执行"这两个动作在具体判断"现在做还是推迟"时，正好可以直接套用两分钟法则的判据。用户问"这封邮件该现在回还是先记着"走两分钟法则，问"整个收件箱该怎么系统性清"走本模型。
- **与[批处理](../batching/SKILL.md)**：本模型第 1 步的"固定处理窗口"就是批处理思想在邮件场景的具体应用；如果用户的问题更广（不止邮件，各类打断源都想集中处理），应引导至批处理这个更通用的模型。

## 记忆钩子

零指的是脑子里的心智周期，不是屏幕上的未读数字；每条只经手一次，分进五个动作里就算完。
