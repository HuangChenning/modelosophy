# IT 招投标数据检索与分析方法

这是报告价值最高、也最容易出错（编造数据）的部分，单独作为一份参考文件详细说明。目标是拿到**近3年（含当年）**目标公司IT相关的招投标/采购记录，并从中提炼出对销售有用的规律。

## 第零步：先判断公司性质，校准预期

开始检索前，先确认目标公司是国企/政府机关/事业单位，还是民营/外资控股企业——这直接决定了能检索到多少公开招投标信息，**不要用同一套预期去要求所有客户**。

- **国企/政府机关/事业单位**：受《政府采购法》及地方公共资源交易管理办法约束，日常IT采购通常需要在政府采购网或地方公共资源交易平台公开发布，这类客户大概率能检索到较完整的招投标记录。
- **民营/外资控股企业（尤其是非上市或未发债的公司）**：不受政府采购相关法规约束，IT采购大多走内部SRM/供应商准入体系，不强制对外公开，检索很可能颗粒无收——**这是正常结果，不是检索能力不足**。遇到这种情况，按下方"第二步"清单该搜的还是要搜一遍（不能因为预判查不到就跳过），确认查不到之后如实在 `trend_analysis` 里写明原因（公司性质决定采购渠道不公开），并给销售一个替代建议：转向已知供应商关系、行业展会、老客户转介绍等非公开招投标渠道去获取信息，而不是让报告在这一板块留白却不说明为什么。

## 第一步：确定检索范围

- **时间范围**：当前年份往前推3个完整年度 + 当前年度至今。例如当前是2026年，检索范围是2023-2026。
- **公司范围**：注意区分集团层面招标 vs 下属子公司/分支机构招标。两者都要检索，但在记录里要注明是"集团"还是具体哪个子公司/分公司发起的，这直接影响后续对接谁。
- **项目类型范围（与本公司业务相关的IT采购）**：
  - 数据库产品/服务（Oracle、MySQL、达梦、OceanBase、TiDB、GaussDB 等及相关维保/迁移服务）
  - 服务器、存储、云主机/云服务采购
  - 信创/国产化替代相关项目
  - 灾备/高可用/数据中心建设
  - 运维外包/驻场运维服务
  - 安全合规（等保测评、数据安全）相关但涉及数据库/基础设施的项目
  - 大型软件开发/系统集成项目中如包含数据库选型也应记录

## 第二步：检索渠道

1. **中国政府采购网（www.ccgp.gov.cn）**：适用于国企、政府机关、事业单位。可按采购单位名称搜索。
2. **地方公共资源交易中心 / 电子招投标平台**：很多省市有独立的公共资源交易平台，搜索"<公司所在省市> 公共资源交易中心"即可定位。国企集团常有自己的"阳光采购平台"或"电子招标投标交易平台"，直接搜"<公司名> 招标公告"往往能找到。
3. **公司官网的"招标公告/采购公告"栏目**：很多大型企业会在官网单独开辟采购信息栏目。
4. **第三方招投标信息聚合平台的公开搜索结果**（如中国招标投标公共服务平台等）：可以作为线索来源，但金额、供应商等关键信息务必以原始公告为准，聚合平台的摘要可能有误。
5. **中标供应商的官方新闻稿/案例展示**：部分中标厂商会在自己官网/公众号宣传中标案例，这类信息可以反向印证，但注意厂商自己的宣传可能夸大金额或范围，交叉验证后再采纳。

## 第三步：记录格式

每条记录填入 `data.json` 的 `it_bidding.records`，字段见 `report-structure.md`。特别注意：

- `amount` 字段填数字（单位：元），方便脚本统一计算和绘图；`amount_display` 保留原始公告里的表述（如"123.46万元"）供报告展示。如果只查到预算金额没查到中标金额（或反之），在 `amount_display` 里注明是"预算金额"还是"中标金额"，不要混淆两者。
- 招标失败、废标、流标的项目也可以记录（说明该项目"未成交"），这类信息对判断客户的真实采购意愿也有参考价值，但不计入供应商中标统计。
- 同一项目如果有多次公告（如中标公告更正），以最终确认的中标公告为准。

## 第四步：供应商汇总（vendor_summary）

1. 对 `records` 里所有 `amount` 非空且确认中标的记录，按供应商名称分组。
2. 供应商名称归一化：同一厂商的全资子公司、地方分公司、曾用名尽量合并统计（例如"XX科技股份有限公司"和"XX科技股份有限公司华东分公司"可合并），合并时保守处理——拿不准是否为同一实体就不合并，避免虚增某供应商的份额。
3. 计算每个供应商的：中标次数（`win_count`）、中标金额合计（`total_amount`）、金额份额占比（`share_pct`，等于该供应商中标金额 / 所有有金额记录的中标总额）。
4. 同时标注每个供应商涉及的项目类别（`categories`），这样能客观看出某供应商是否专精数据库类项目，还是综合集成商——这是描述客户的供应商格局，不需要延伸判断"我方该怎么切入"。

## 第五步：采购趋势分析（trend_analysis）

基于整理出的 `records` 和 `vendor_summary`，尝试回答以下问题（能回答几个算几个，答不出来的不要硬编）。这些问题的落点是"客户的采购行为呈现什么客观规律"，不是"我方该如何应对"——后者属于另一个技能（产品匹配/攻坚方案层）的工作，写到这一步为止就停下：

- **预算趋势**：近3年同类项目的金额是在增长、持平还是收缩？
- **技术选型趋势**：是否能观察到从某类产品转向另一类（例如从 Oracle 转向国产数据库）的迹象？是否有信创/国产化相关项目占比上升？
- **供应商集中度**：是否长期由某1-2家供应商垄断，还是每次招标都换新供应商？这本身是一个客观事实，不必延伸判断"切入难度"。
- **招采节奏**：能否看出该公司IT类招标的大致周期（比如每年Q1密集招标、或3年一个大合同周期）？这一条只需客观描述节奏本身。

**再次强调**：以上每一条分析都必须能在 `records` 里找到对应的具体项目作为证据。如果检索到的招投标记录数量很少（比如少于3条），如实说明"公开渠道可检索到的该公司IT相关招投标信息有限，以下趋势判断基于有限样本，建议在拜访中进一步核实"，不要为了凑出"趋势"而过度解读少量数据。如果分析到这里忍不住想写"这对我们意味着……"，把这句话删掉，改成放进 `open_questions`（客观地列成一个待核实问题）或干脆不写——那部分判断属于另一个技能。
