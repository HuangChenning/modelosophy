# 决策链四角色模型

v3.0 参考了华为 MCR（Manage Client Relationship）客户洞察体系中"客户决策链洞察"维度的角色分类方法，用来让 `decision_chain.roles` 的信息组织得更有结构，而不是想到哪写到哪。**这套模型只用来客观描述"客户内部谁负责什么、谁的话语权更重"，不用来评估"这个人对我方/对我们产品的态度"——后者是另一个技能（产品匹配/攻坚方案层）的工作，本文件里不涉及。**

## 四个角色

| 角色 | 全称 | 职能 | 分析要点 |
|------|------|------|---------|
| UB | User Buyer（使用者） | 实际使用系统/产品的一线人员或团队 | 使用体验、日常痛点、对现有系统的抱怨（如公开可查） |
| SP | Specifier / Purchaser（建议者） | 负责技术评估、方案选型 | 技术选型标准、评估维度、公开发表的技术观点 |
| TB | Technical Buyer（把关者） | 采购流程、合规/资质审核 | 采购流程要求、合规标准、招标文件里体现出的审核逻辑 |
| EB | Economic Buyer（决策者） | 最终预算拍板 | 预算权限范围、公开可见的决策动机（如战略优先级、监管压力） |

在 IT/数据库相关的采购场景里，这四个角色常见的对应关系（不是唯一映射，仅供参考）：

- **UB**：运维团队、DBA、业务系统的一线使用部门
- **SP**：信息中心/技术部门里负责技术选型评估的人（如架构师、技术负责人）
- **TB**：采购部、招投标合规审核相关岗位
- **EB**：信息中心/CIO/主管科技的副总，或对预算有最终拍板权的更高层级领导

**这套映射不是绝对的**，具体到某个客户，同一个人可能身兼多个角色（比如小型机构里信息中心负责人可能同时是SP和EB），也可能有华为模型里没有覆盖的岗位（比如国企/政府机关里常见的"分管领导"）。填 `role_type` 字段时按实际观察填写，映射不上就留空，不要为了凑齐四个角色而生搬硬套。

## 每个角色的分析要点

对应 `report-structure.md` 中 `decision_chain.roles` 的字段：

1. **具体人员**（`name`）：姓名/职位。查不到具体姓名，`name` 留空，但仍然要把 `role` 和 `role_type` 填出来——组织结构本身就是有价值的信息，不必等有名字才记录。
2. **岗位职责**（`notes` 里体现）：这个岗位大致负责什么。
3. **决策权重**（`decision_weight`，可选）：高/中/低，基于岗位在决策链里的位置判断（比如"预算最终拍板人"通常是高，"日常使用者"通常是低但可能是重要的意见来源）。
4. **沟通风格**（`communication_style`，可选，见下方"沟通风格四类型"）：只有在有公开发言/专访/文章能体现出这个人的沟通/决策偏好时才填，不要凭岗位刻板印象猜测（比如不要因为"是技术负责人"就默认他是"分析型"）。
5. **马斯洛需求层次**（体现在 `notes` 里，不单独设字段）：如果公开资料（专访、演讲）能体现出这个人的关注点更偏向"完成任务的安全感/稳定性"（安全需求）还是"个人职业发展、行业影响力"（尊重/自我实现需求），可以客观记一笔，帮助理解这个人可能更在意什么，但不要过度解读几句话就下结论。

**明确不做的事**：华为原始模型里这一步通常还会评估"与我方关系状态"（如 -1 不认可 / 0 中立 / 1 接触 / 2 支持 / 3 教练）。**这个字段不要加进 `data.json`。** 这份报告的读者应该看到的是"客户内部的权力结构长什么样"，而不是"这些人有多支持我们"——后者需要销售自己的一手接触经验，且天然带有"我方视角"，不属于这份客观情报报告，也容易在还没接触客户之前就凭空打分。

## 沟通风格四类型

仅在有充分公开信息支撑（专访、公开演讲、媒体报道里的行事风格描述）时才使用，不要仅凭职位或姓名猜测：

- **控制型**：决断快、重结果、不喜欢被过程管理，公开发言里常见"效率""执行力""结果导向"等表述
- **倡导型**：善于讲愿景、重关系、公开发言里常见对"团队""合作""共赢"的强调
- **分析型**：重数据、重流程、决策前要看充分的论证材料，公开发言里常见对"标准""流程""风险控制"的强调
- **亲切型**：重稳定、重共识、不喜欢激进变化，公开发言里常见对"稳妥""循序渐进""长期关系"的强调

如果检索不到能支撑判断的公开信息，`communication_style` 字段留空，不要瞎猜——瞎猜出来的沟通风格标签比没有更危险，容易误导后续接触方式。

## 权力地图（`decision_chain.diagram_nodes` / `diagram_edges`）

沿用 v2.0 的 SVG 关系图渲染逻辑：`level` 表示层级（0为最高），`stance` 只表示"对新方案/外部供应商的态度倾向"这一组织行为研究判断（`supportive`/`resistant`/`neutral`/`unknown`），不是"对我方"的态度评分，写法参考 `report-structure.md` 里的现有说明，v3.0 未改变这部分逻辑。UB/SP/TB/EB 角色分类可以体现在节点的 `sublabel` 里（比如"技术开发部负责人（SP）"），帮助读图的人快速识别每个节点在决策链里的功能定位。
