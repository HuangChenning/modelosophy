# FAB 框架 Feature–Advantage–Benefit

## 这是什么

**FAB** 是一套**产品/功能说明**结构：把一个客观特性，逐层翻译成用户能感知、能衡量的价值。

| 字母 | 含义 | 判据 |
|---|---|---|
| **F** Feature | 特性 | 客观描述，去掉任何具体用户主语后依然成立 |
| **A** Advantage | 优势 | 包含一个动词短语，描述用户因此新获得的能力 |
| **B** Benefit | 利益 | 落到用户或组织能衡量、感知、验证的结果 |

它起源于 Xerox 1968 年推出的 Professional Selling Skills（PSS）培训课程（又称 Selling by Needs Satisfaction），Xerox 为此投入约 1000 万美元并专门成立 Xerox Learning Systems 部门推广，此后成为 B2B 销售培训的经典底层结构，并延续到今天的 SaaS 产品营销实践。

它解决的是：**避免"堆功能列表"式的自说自话**，强迫每个 Feature 都走完到 Benefit 的完整链条，而不是假设客户会自己脑补出价值。

## 什么时候用

- "帮我写产品介绍/说明书/功能页"
- "这个功能怎么讲才能让客户明白有什么用"
- 直接说 FAB / 功能-优势-利益
- 宣传手册的功能章节、销售话术里介绍产品能力的部分

**不要**当主模型：

- 用户要靠情绪紧迫感驱动立刻购买/点击的短文案（广告、朋友圈、落地页开场）→ [`pas`](../pas/SKILL.md)
- 用户要汇报/备忘录的问题定义开场 → [`scqa`](../scqa/SKILL.md)
- 产品没有具体客观特性可描述，纯粹是品牌/情感叙事 → FAB 无从下手，需先有可描述的 Feature

## 怎么用（执行步骤）

1. **写 F（特性）：客观描述，不带用户视角。** 判据：把这句话读一遍，如果去掉任何"你/用户/团队"这类主语后依然成立（比如"支持256位加密""每5分钟自动同步一次"），才算合格的 Feature；如果不去掉主语就读不通，说明已经混入了 Advantage。
2. **写 A（优势）：说明用户因此新获得了什么能力。** 判据：这句话必须包含一个动词短语，描述"用户现在能做到（以前做不到）的事"（如"团队不用手动重复设置流程"）；如果只是重复 Feature 换个说法，没写出"能做什么新的事"，就没走到位。
3. **写 B（利益）：落到可衡量或可感知的结果，按受众分别陈述。** 判据：这句话是否给出一个具体的结果（省了多少时间、降低了什么风险、减少了什么摩擦），而不是空洞形容词（"更高效""更省心"）。**同一个 Advantage 可以分叉出多条 Benefit**：面向决策者写业务层结果（成本、风险、可衡量指标），面向实际使用者写体验层结果（更少打断、更省力）——不要用一句话强行同时满足两种受众。
4. **自检链条完整性。** 逐句检查 F→A→B 是否环环相扣：抽掉 A，B 是否还能从 F 直接推出？如果不能，说明中间有断层，客户很可能也接不上，要显式补全，不能假设对方会自己脑补。
5. **自检语气。** Benefit 是否仍是客观可验证的结果，而不是情绪化承诺（"从此摆脱焦虑""倍儿有面子"）？若变成了情绪渲染，说明已经越界到 PAS 的地盘，应回到"可衡量结果"上。

## 例证

**Xerox Professional Selling Skills（1968）**：Xerox 投入约 1000 万美元开发这套培训课程并成立专门部门推广，是把"讲清楚产品价值"从销售员个人经验总结为可复制方法论的关键历史节点，此后成为几十年 B2B 销售培训的基础结构。

**Slack（当代 SaaS 案例）**：Feature「工作流自动化」→ Advantage「自动化处理重复任务，团队不用手动设置」→ Benefit 对决策者是「可衡量地减少会议开销」，对一线使用者是「更少打断、更少上下文切换」——揭示同一条 Advantage 如何按受众分叉出两条不同的 Benefit，而不是只写一句笼统的"更高效"。

**Dropbox（当代 SaaS 案例）**：Feature「云存储 + 256位加密 + 跨设备同步」→ Advantage「无需实体硬盘即可存储和共享大量数据」→ Benefit 对决策者是「降低误删/安全泄露风险」，对使用者是「随时能访问文件的安心感」——揭示 Benefit 层必须具体到"降低了什么风险/带来了什么安心"，而不是停在 Advantage 层就收尾。

## 什么时候不适用（边界）

- **需要制造购买紧迫感的短文案场景**：FAB 靠逻辑清晰度建立理解，不主动制造紧迫感或情绪张力 → 要驱动立刻行动，改用 [`pas`](../pas/SKILL.md)。
- **产品没有具体客观特性可描述**：纯品牌故事、情感叙事、愿景类内容缺少可锚定的 Feature，FAB 无从拆解 → 改用叙事类框架。
- **B2B SaaS 双受众未拆分时的通用陈述**：对决策者和一线实践者用同一句 Benefit，会导致"要么签单容易但用户上手慢，要么产品好用但决策者签不下"的两难——必须显式按受众分别写 Benefit，而不是硬凑一句兼顾两者的话。
- **受众已经完全理解产品、只想快速对比参数**：此时把每个功能都完整走一遍 F→A→B 会显得冗长啰嗦，可只保留 Feature 级的对比表。

## 常见误用

- **只列 Feature 或停在 Advantage，就以为讲完了（"feature bragging"）**：客户听完一堆技术参数却不知道对自己有什么用 → 回到步骤 3，补全到可衡量的 Benefit。
- **假设客户会自动把 Feature 关联到 Benefit**：链条中有断层却没显式说完 → 回到步骤 4 检查环环相扣。
- **把 FAB 当成必须逐字背诵的固定话术**：机械念完三句显得生硬、像单向推销 → FAB 是引导对话的思维框架，不是要背的台词，应结合具体客户场景调整措辞。
- **B2B 场景下用一句 Benefit 兼顾决策者和使用者**：导致签单和留存其中一头出问题 → 回到步骤 3，按受众拆分。
- **把 Benefit 写成情绪化承诺，与 PAS 混淆**：用户要的是讲清楚功能价值，却写成"从此摆脱焦虑"这类情绪渲染 → Benefit 应保持客观可验证，情绪驱动的文案改用 [`pas`](../pas/SKILL.md)。

## 相关模型

- **与[PAS](../pas/SKILL.md)**：**硬区分。** FAB 从产品**特性**出发，靠逻辑清晰度建立理解和信任，不主动制造紧迫感；PAS 从读者**问题**出发，靠情绪紧迫感驱动立刻行动。用户说"说明这个功能是干嘛的/产品页/功能对比/宣传手册功能章节"→ FAB；说"写一段让人立刻想买的广告/朋友圈文案"→ PAS。两者可在同一份宣传手册里配合：开篇用 PAS/BAB 钩住痛点，功能章节用 FAB 逐条讲清楚价值。
- **与[SCQA](../scqa/SKILL.md)**：SCQA 是问题定义与逻辑开场结构，与 FAB 的产品说明目的完全不同，一般不会混淆；但若用户想拿 FAB 硬套整篇文档的开场逻辑，应提醒改用 SCQA。

## 记忆钩子

先说它是什么，再说它能让你做到什么，最后说这对你到底值多少。
