# TOC 约束理论 Theory of Constraints

## 这是什么

**约束理论（TOC）**：任何目标系统的绩效（常见指标：有效产出 Throughput、库存 Inventory、营运费用 Operating Expense）都受制于**极少数约束（constraints）**——限制系统达成更高目标的那一环。改进应**聚焦约束**，而不是平均用力「到处优化」。

Eliyahu Goldratt 在《目标》（The Goal）等著作中推广的操作核心是**五聚焦步骤（Five Focusing Steps）**：

1. Identify — 识别约束  
2. Exploit — 利用约束（让约束满负荷做「对的事」，先不砸钱）  
3. Subordinate — 其他一切服从约束节奏  
4. Elevate — 若仍不够，再提升约束能力（扩容、外包、改设计）  
5. Repeat — 防止惰性；约束转移后重新识别  

配套思想包括：局部效率可能伤害全局；用缓冲保护约束；「鼓–缓冲–绳子」（DBR）等排程直觉。

## 什么时候用

- "产能/交付总卡住，局部都很忙"
- "加了人/设备，整体吞吐几乎不变"
- "哪里是瓶颈？关键链怎么排？"
- 直接提 TOC / 约束理论 / Goldratt / DBR

**不要**当主模型：

- 单次事故「为什么坏了」的因果链 → [`five-whys`](../five-whys/SKILL.md)
- 发明原理/技术矛盾破解 → [`triz`](../triz/SKILL.md)
- 反馈回路与系统结构诊断（非吞吐瓶颈）→ [`systems-thinking`](../../systems-classic-effects/systems-thinking/SKILL.md)
- 优先级矩阵（紧急重要）→ [`eisenhower-matrix`](../../efficiency-execution/eisenhower-matrix/SKILL.md)

## 怎么用（执行步骤）

1. **定义系统目标与度量。** 写清「系统」边界与成功指标（如单位时间完成的有效产出、交付周期）。判据：优化局部 KPI 是否可能与该目标冲突？若会，标出危险 KPI。
2. **识别约束（Identify）。** 找限制吞吐的资源/政策/市场：哪里队列最长、利用率持续近满、下游常等上游？输出一句话：「当前约束是 X（类型：资源/政策/市场）」。一次只认定**一个主约束**。
3. **利用约束（Exploit）。** 在不增加约束产能的前提下，消除约束上的浪费：只做高贡献工作、减少换型空转、保证质量一次做对、勿让约束闲置等闲活。判据：约束有效工作时间是否上升？
4. **服从约束（Subordinate）。** 非约束环节按约束节奏供料/接收：宁让非瓶颈闲一点，也不要灌爆约束或制造过量在制品。设置缓冲保护约束。判据：非瓶颈「效率」下降但系统吞吐上升 → 通常是正确信号。
5. **提升约束（Elevate）并再循环。** 若 Exploit+Subordinate 仍不够，再投资扩容或改设计；完成后检查约束是否转移，回到步骤 2。**禁止**在未利用前就昂贵提升。
6. **政策约束检查。** 若物理资源有余但规则禁止（批次过大、错误考核、审批闸门），把政策标为约束并改规则——常比买设备更便宜。

## 例证

**《目标》工厂叙事（教学原型）**：机器人局部效率很高，但整厂出货上不去——约束在别处，局部「高效率」只堆库存。揭示 TOC 核心：**局部最优 ≠ 系统最优**。

**知识工作瓶颈**：团队「大家都忙」，实际约束是唯一能做架构评审的两人——其他人并行开工制造返工。Exploit：评审时段不受会议侵占；Subordinate：未过评审的需求不进入开发主列。揭示：约束常是**稀缺认知资源**，不是工位。

**市场约束**：产能闲置但订单不足——约束在市场/销售漏斗，再扩产只增加费用。揭示：约束类型决定动作，不是永远「加机器」。

## 什么时候不适用（边界）

- **目标本身错误或多元冲突未对齐**：TOC 优化错误目标会更快到达错误终点；先对齐目标。
- **强随机、强外部冲击主导**：短期救火优先于稳态瓶颈管理。
- **把人标签化成「永久瓶颈」**：约束应指向角色/流程/政策，并允许转移；避免羞辱式管理。
- **创新早期无稳定流程**：过早 TOC 可能固化错误价值流；先稳定基本流。

## 常见误用

- **到处优化**：每个工位都上满效率工具 → 先找约束。
- **未利用就扩容**：先买设备/加人 → 违反 Exploit→Elevate 顺序。
- **用局部利用率当成功**：非瓶颈 100% 忙碌当成绩 → 可能在伤害吞吐。
- **与 5Why 混用**：问「谁是瓶颈人」变成追责链 → 5Why 管失效因果；TOC 管稳态吞吐约束。
- **与帕累托混淆**：80/20 找重要少数因子；TOC 专指**限制系统目标**的约束环节——可重叠但问题不同。

## 相关模型

- **与[5Why](../five-whys/SKILL.md)**：5Why 下钻单次/反复失效的因果；TOC 管理持续吞吐的约束。复盘故障走 5Why；交付上不去走 TOC。
- **与[杠杆点](../../systems-complexity/leverage/SKILL.md)**：杠杆点谈干预系统结构的高影响点；TOC 的约束是运作层高影响点之一，可连用但不要把任何杠杆都叫「约束」。
- **与[系统思维](../../systems-classic-effects/systems-thinking/SKILL.md)**：系统思维画回路与延迟；TOC 给「先动哪一环」的吞吐聚焦法。结构不明时先系统扫描，稳态交付问题用 TOC。
- **与[帕累托](../../systems-classic-effects/pareto-principle/SKILL.md)**：帕累托排重要性；TOC 要求识别**限制目标实现**的那一环（可能不是「最大的成本项」）。
- **与[PDCA](../../efficiency-execution/pdca/SKILL.md)**：TOC 五步可嵌入 PDCA 循环做持续约束管理。

## 记忆钩子

系统快不快，取决于最慢且最关键的那一环——先喂饱它，别让别人空忙。
